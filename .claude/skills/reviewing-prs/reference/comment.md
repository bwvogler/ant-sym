# The review

Contents: [Posting the review](#posting-the-review) · [Inline suggestions](#inline-suggestions) · [First review](#first-review) · [Re-review](#re-review) · [After posting](#after-posting) · [Owner summary](#owner-summary-in-the-chat-not-on-github)

One GitHub review per round, event `COMMENT`. Its **body is the whole review**; one-line fixes are also inline suggestions on their lines. Plain words; numbers over adjectives; every finding has a `file:line`, what you saw (the evidence), and a suggested fix. Omit a body section that would be empty, except Merge mechanics and Not re-measured, which always appear.

## Posting the review

1. `mcp__github__pull_request_review_write` method `create`, with `commitID` = the head SHA you reviewed and **no** `event` and no body: this opens a pending review. (One pending review per user per PR; if one is left over from a failed attempt, `delete_pending` first.)
2. For each one-line fix, `mcp__github__add_comment_to_pending_review`: `path`, `line` (the line number in the PR's version of the file), `side: RIGHT`, `subjectType: LINE`; for a few adjacent lines add `startLine` and `startSide: RIGHT`. The line must be inside the PR's diff; if GitHub refuses it, leave that item in the body only.
3. `pull_request_review_write` method `submit_pending`, `event: COMMENT`, `body` = the review body below, footer last. Never `APPROVE` or `REQUEST_CHANGES`.

Nothing is visible until step 3, and the author's session gets one event for the whole review. If a step fails, `delete_pending` and start again rather than posting half a review.

## Inline suggestions

Only for a fix that replaces the commented line(s) and needs no discussion: a stale comment, a lint warning, a wrong constant, a typo, a missing guard on one line. The block holds the replacement text exactly, so the author (or an agent) can apply it as is:

````markdown
N2. The env override this mentions was removed in #43.
```suggestion
  // Spacing between gyne brood, in cells (GYNE_SPACING).
```
````

Rules:
- Start with the item number, and list the item in the body too (`N2. Stale comment — royal.ts:47 (inline suggestion)`).
- A suggestion must be right as written: copy the surrounding code, keep the indentation, and check it would compile. If you're not sure of the exact text, describe the fix in the body instead.
- No inline comments for blockers, should-fixes that span lines or files, missing tests, decisions or questions. They stay in the body, where an agent reads them in order.

## First review

```markdown
## Review of <head sha7> — **<Approve | Approve with N should-fix | Changes requested>**

<Two or three sentences: what the PR does and whether it does it, in the owner's words, with the headline number.>

### Blockers
**B1. <Short claim>** — `web/src/colony/game.ts:292`
<What happens, measured: "seed 3, tick 4,210: foodTotal rises by 14 with no source">. <Why it matters.>
Suggested fix: <the smallest change that fixes it, as code if short>. <How you checked the fix, if you did.>

### Should-fix
**S1. <Short claim>** — `file:line`
<Evidence. Mutation table if it's about a test.>
Suggested fix: <…>

### Decision for the owner
**D1. <The question>** — <the options, each with its cost and effect in one line. No recommendation unless asked, or a clearly marked one.>

### Nits
- `file:line` — <one line each>

### Mutation checks
| mutation | caught by |
|---|---|
| <one-line change> | <test name, or **not caught**> |

### Merge mechanics
- Against main (<main sha7>): <clean | conflicts in a, b — resolutions>. <Trial merge: N tests pass.>
- Against open PRs: <#n clean; #m conflicts in x>. <Who merges first.>
- <Stacked on #n: merge #n first, then retarget to main.> Squash.

### Checked and fine
- <tsc clean; N tests pass; lint W (main W); build ok; goldens unchanged | moved as stated; precache …; SAVE_VERSION …; versions bumped …>
- <Each focus-list item you checked and found right, briefly.>

### Not re-measured (slow)
- <test:slow, G′ 20 seeds, 12-minute game runs, side-bench … — what each would tell, if the owner wants it.>

<details>
<summary>Helper's report (deep pass on <head sha7>; the verdict above is the lead's)</summary>

<The helper's report, pasted whole. Prefix each item the lead checked with ✓ (confirmed: it is in the review above),
✗ (did not hold: one line why) or ? (not verified by the lead).>

</details>

---
_Generated by [Claude Code](https://claude.ai/code)_
```

Number items (B1, S1, D1, N1) so a re-review and the author can refer to them.

**The helper's report** goes in the collapsed `<details>` block, only when a helper ran. Keep it whole, so the discussion is on record, but mark each item: ✓ confirmed (and in the review), ✗ did not hold (with one line why), ? not checked. Nothing in the block is the verdict; the sections above it are. A helper never posts its own comment, so a PR has one review per round.

## Re-review

Posted the same way (one review, `COMMENT`). Before it, read the earlier inline threads (`pull_request_read` get_review_comments): resolve each thread whose fix landed (`pull_request_review_write` method `resolve_thread`), and answer any reply the author left there.

```markdown
## Re-review of <new sha7> (since <old sha7>: <n> commits) — **<verdict>**

| item | status | note |
|---|---|---|
| B1 reserve conjures food | resolved | <how; mutation now caught by `game.test` "founding conserves food"> |
| S2 found() idempotent | partly | <what's left> |
| N3 stale comment | not | |

### New in this push
<Findings in the first-review shape, numbered on from the last (S4, N5 …).>

### Merge mechanics
<Re-run: main has moved since the last review.>

### Checked and fine / Not re-measured (slow)
<As above.>

---
_Generated by [Claude Code](https://claude.ai/code)_
```

## After posting

A submitted review's body can't be edited with these tools, and a second review would compete with the first. Follow up with short PR comments (`mcp__github__add_issue_comment`), each naming the review and the item, footer last:

- A mistake of yours: `Correction to the review of <sha7>, S2: <what was wrong and what is right>.` For an inline item, reply on its thread instead (`mcp__github__add_reply_to_pull_request_comment`).
- The owner decides an open item: `Owner's decision on D1 (review of <sha7>): <decision>; filed as ja-xxx.`
- The next re-review lists both in its status table.

(Older reviews were single PR comments; those you can still edit with `mcp__github__update_issue_comment`, marking the change "(Corrected …)" or "(Edited …)".)

Ideas the owner raises that are not this PR's job: file beads (SKILL.md stage 7), then a short note on the PR:

```markdown
Owner's follow-ups filed as beads: ja-5hm (<title>), ja-506 (<title>, after ja-5hm and ja-8fd). Interim for this PR: <the gate the owner chose>.

---
_Generated by [Claude Code](https://claude.ai/code)_
```

## Owner summary (in the chat, not on GitHub)

Short: what the PR does (in plain words), the verdict with the link, what is left and on whom, the merge order across open PRs, and the decision that is theirs. Expand any term the owner hasn't used.
